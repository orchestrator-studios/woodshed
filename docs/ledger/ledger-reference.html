What this system does

Work happens in many sessions, across many workspaces, on multiple machines — concurrently, with no session aware of the others. Off that activity the system captures two kinds of data: automatic telemetry about the sessions themselves, and the curated record of the work those sessions throw off. One service holds both, and aggregates them back into one picture.

processing waiting dormant telemetry in logged work in context out
The two planes, and exactly what each consists of

Session telemetry automatic

One object: the Session — lifecycle state declared by hook signals as it lives (active, waiting, processing, run, dormant). Machine-generated; no judgment, no content. Answers: what is running, where, right now? Its surface is the board. (Logging an event also writes it — invariant 9.)

The work record curated

Three objects, thrown off by what those sessions do and admitted by judgment:

Eventwhat happened — immutable, one line + bullets, belongs to one stream
Streama thread of work under management — state, next action, open loops
Deliverablewhat was made — a name plus exactly one home; persists and is advanced over its life
Runa bounded stretch of work on one deliverable — declared open, declared closed

Answers: what has been done, what's in flight, what's next? Its surfaces are the orientation, recall, and the board's record columns.

These five objects — Session; Event, Stream, Deliverable, Run — plus the Workspace a session runs in, are the system's entire vocabulary. Every panel in this book moves those six things and nothing else. Plane one emits plane two: a session's activity is where every event, run, and stream update comes from, and attribution stitches them — every event carries its session, every run its session and its deliverable, every session at most one stream.

The seven behaviors — what each plane gets, and what spans both
  1. telemetry Tracks sessions. Every Claude Code session's lifecycle — active, dormant, archived; waiting, processing — declared by hook signals and API calls, never hand-maintained, never inferred.
  2. record Records events. Immutable, timestamped statements of what happened — a ship, a decision, a send, a state change — each belonging to exactly one stream.
  3. record Maintains streams. One management record per thread of work: current state, the single next action, open loops, staleness.
  4. record Registers deliverables and the runs that make them. Each deliverable is a name plus exactly one home (repo, Drive, sheet, published page); the ledger stores the record, the payload stays at its home. Each run is a bounded stretch of work against one deliverable, declared open and declared closed.
  5. record Answers recall. Queries across events, streams, and deliverables return dates, links, and current state.
  6. both Serves its own views. The board data structure (telemetry, enriched by the record) that the BotBeam view renders, and the session-start orientation (the record) — projections of the one store; no client computes a view.
  7. both Enforces its rules in code. Schemas, state transitions, atomicity, and attribution are validated by the service on every write. A client can be wrong; the store cannot.

How it runs

The system is a live database of sessions and events, kept current by two independent moving parts that never talk to each other — they only talk to the service. This panel is the operational picture: who runs, when, and what each one writes. If you read one panel to understand how the thing actually works, read this one.

Hooks are NOT part of the skill. This is the single most confusing thing about the system, so state it plainly: the skill is instructions loaded into Claude's context and acts only when Claude decides to act. Hooks are wired in ~/.claude/settings.json, fire from Claude Code's own lifecycle, and run session_event.py in a separate OS process with no Claude and no judgment involved. A hook fires whether or not the ledger skill was ever loaded — which is exactly why the sessions half of the database is complete by construction and the events half is not. They share a folder in the repo; they share nothing at runtime.
The two moving parts — what runs them, and what each maintains

1 · Hooks telemetry

Runs: automatically, on five Claude Code lifecycle moments.
Trigger: the CLI itself, via settings.json.
Writes: session rows — status, turn_state, timestamps.
Judgment: none, and none allowed.
If it breaks: the board goes stale. The record is unaffected.

2 · The skill record

Runs: when Claude judges that work produced an outcome.
Trigger: Claude's own activity — not the user, not a timer.
Writes: events and streams (and the emitter's liveness).
Judgment: everything — this part is judgment.
If it breaks: history is silently lost. Nothing can recover it.

What this means in practice
  1. The sessions half maintains itself. You do nothing, Claude does nothing, and the board stays true — because hooks are involuntary. The only manual act in the whole telemetry plane is archive, when you want a finished card gone.
  2. The events half depends entirely on Claude's discipline. No sensor can see that a diff was a deliverable. If Claude doesn't log it, it never happened as far as the database is concerned — and nothing later can reconstruct it. That is why logging is written as a standing duty, not a feature the user invokes.
  3. The two halves meet in exactly one place. Logging an event writes the emitting session's liveness (invariant 9). Nowhere else does the record plane touch the telemetry plane.
  4. The service is the only writer. Hooks and skill both send intent over HTTP; the service validates it, stamps it, and commits it. No client writes storage, and no client computes a view.
So who maintains the database? The service maintains it; two clients feed it. One (hooks) is machinery that runs without anyone deciding anything — it keeps the sessions current. The other (the skill) is Claude exercising judgment — it keeps the events current. Calling the whole thing "the skill" is the mistake: the skill is one of two feeds, and the only one that can forget.

Session lifecycle

Sessions move through these states. Every transition is a hook signal or an API call landing in the service's state machine, and every one writes the status it declares — status is a stored column, exactly like turn_state; nothing infers a lifecycle state from timestamps. A crash fires no signal, so a crashed session keeps its last declared status until a repair mechanism is added — deferred, the same pattern as the turn_state cleanup. dormant means “declared closed” (SessionEnd, or unarchive); dormant sessions leave the board only when the user clears them (archive), which is the one manual act in the system.

Three states, and no fourth. Rev 20 retired expired. It was never a state of the session — it described whether a file still sat on one machine's disk, which is a different kind of fact and the source of every edge case the lifecycle used to carry. Claude Code deletes transcripts on its own retention clock (cleanupPeriodDays, 30 days by default), so “the transcript is gone” reduces to “this session is older than the retention period” — computable from last_event_at, never worth observing. And the ledger's record of a session should outlive the local file that session was typed into. The whole sweep apparatus that fed it is retired with it.
Transition → signal → fields written — the exact writes, per transition

Universal writes first: every hook signal, whatever its type, also writes last_event_at = now, resets and — every signal except SessionEnd — writes status = "active" and clears archived_at: any sign of life is declared, not derived. Session cheat sheet

Written from the board backwards: three rules that say what you're looking at, then every transition the board can show — cornered, one cause each. The facts come last; they anchor the rules, you don't memorize them.

Rule 1 — what's listed
The board lists every session you ever prompted, minus the ones you archived. Nothing else, ever. A card you don't want → archive it (the one manual act in the whole system). A card you expected but don't see → it was never prompted, or you archived it — there is no third reason.
Rule 2 — what the glyph says
GlyphStateMeansYour move
processingClaude is mid-turnnone — it's working
⚡open runworking on a named deliverable — the card shows which, and for how longnone — it's making something
waitingthe turn is finishedyours — it's waiting on you
⚡waiting + open runwork parked mid-run — a run is still open but the turn handed back to youyours — answer, and the run resumes
dormantsilent — exited, crashed, or idle; unknowable and equivalent, all resumableresume it, or archive it away
The bolt is orthogonal to the turn glyph — rev 21 ruling. The old run was a sub-state of processing, so ring+⚡ was impossible by construction. It is not only possible now, it is common: a run spans whatever turns it takes, and Claude stopping to ask you something does not end the work. Render the two channels independently — the circle answers whose move is it, the bolt answers is a deliverable being worked. All four combinations are legal and each means something.
Rule 3 — nothing on this board ages
No windows. Rev 21 deleted the last one. The ⚡ is lit by an open run and goes out when that run is declared closed or abandoned — never on a timer. Every glyph on the board now traces to a stored, declared fact. A card goes gray only when its session declares dormant (clean exit, or unarchive). A crashed session stays green, and a crashed session's run stays open, until a repair mechanism is added — the one known lie on the board, accepted for now (deferred).

Objects at a glance

The system's entire vocabulary: six objects. Workspace and Session originate in Claude Code (the service annotates the Session — that annotation is the telemetry plane); Event, Stream, Deliverable, and Run are the ledger's own — together they are the work record. Session status and turn state are stored, declared by the signals and calls that cause them; the only computed fields are filters and display rollups (relevance, staleness, attribution, elapsed).

Rev 21 — the two nouns of making. A Deliverable is a thing that was made; it persists and is advanced over its life. A Run is a bounded stretch of work against exactly one deliverable, declared open when the work starts and closed when it ends. The old run — a bolt computed from a decaying last_run_at timestamp — is deleted: it inferred a lifecycle state from a clock, which is precisely what invariant 2 forbids.

Session CC telemetry

A persistent Claude Code conversation: durable id and transcript, resumable across process runs. The object is Claude Code's; the service keeps a record about it. The record stores facts and two declared statuses — status and turn_state — each written only by the signal or call that causes its transition, never inferred from timestamps; see Session lifecycle for the exact writes. Two writers, one record. Stream ledger record

A named thread of work for which the ledger is the management surface. A stream is a service record, read and written only through the API.

Lifecycle

active → closed via POST /ledger/streams/{id}/close. Closure logs its own event. Updates replace whole fields; the service never merges prose.

A stream is born with an event and closed only by the user. There is no separate create call: stream_id on POST /ledger/events is the slug the event belongs to, and when that slug is new it arrives with create_stream carrying the opening fields — one atomic transaction, so a stream can never exist with no event behind it. At the other end, a stream stays active until the user explicitly closes it (Cliff's ruling, rev 20). Claude never closes one on its own judgment and never proposes closing one because it has gone quiet — staleness is reported, never acted on. Slugs are permanent: events reference them, so a rename orphans history.
Relationships

Has many events and deliverables. Sessions are attributed by the service's rule, ≤1 per session; writes into the ledger service itself never re-attribute (rules out the v1 failure where a session's own journal write rebranded it ledger-meta). Attribution is only the board's label — a session's events and deliverables may span any number of streams, so the working relationship is many-to-many.

The meta stream. meta is a permanent built-in stream for ledger-system work: it satisfies “every event has exactly one stream,” never closes, never attributes sessions, and stays out of the working index.

Event ledger record

Something that happened: a decision, a ship, a send, a state change. Events are append-only — never edited, never deleted. Carrying both session_id and stream_id, events (with deliverables) are also the join records of the session↔stream many-to-many: the streams a session worked are the distinct stream_ids of its events and deliverables, and vice versa.

An event is a point; it has no in-flight phase. Most events are recognised only at the moment they happen — a decision lands, a message goes out — so there is no earlier moment at which one could be declared. That asymmetry is why events are a single call and runs are two. Events do not require a run, and a run is not an event. How a deliverable's advancement is announced in the event feed is open — see the Deliverable panel.

What qualifies as an event

Deliverables shipped, decisions made, external communications sent, streams changing state, open loops created or closed. Routine lookups, intermediate work, and anything reconstructible from git do not qualify. The full rules — what the service enforces versus what the skill judges — are on the Event emission rules panel. Events are created only by POST /ledger/events, which also writes the emitting session (invariant 9).

Deliverable ledger record

Rev 21 — un-deferred and renamed. Formerly “work product,” deferred since rev 18. The name was wrong and the concept was doing nothing. It returns because runs need something to be runs of. Not called “artifact” — that word is spoken for three times over (claude.ai Artifacts, the orchestra artifacts skill, the Artifact Tracker), and ambiguity here would be expensive.

A thing that was made. The ledger stores the record; the payload lives at its home. Content is never copied into the ledger.

A deliverable persists and is advanced. This is the whole reason it is a noun rather than a property of an event: the Ledger Book is one deliverable at revs 18 → 19 → 20 → 21, not four unrelated events. An event is a point in time and cannot carry a thing's identity forward across the work that shapes it. A deliverable can.

Mutability, and why it is not a contradiction. Events are immutable (invariant 3) and a deliverable is mutable. That is the point of splitting them: the record of what happened never changes, while the thing that was made is supposed to. An earlier draft tried to give an event two moments — open and close — which forced a carve-out in immutability. Moving the mutation onto a noun that was always going to change removes the conflict entirely rather than negotiating with it.
Home policy. Landed somewhere real → register the link. Email sent → the event is the record; the mail system holds the payload. Inline-only deliverable → it gets a home first, then a registration. Per standing doctrine the home is the file in its owning repo; a published link is an extra, never the source.
Open — deliverable ↔ event. Deliverables are owned by streams and advanced by runs; how (and whether) each advance also writes an event in the feed is deliberately unsettled as of rev 21. The expectation is that it falls out once runs are real. Until it is decided, nothing in the service should assume a one-to-one between a closing run and an event.

Run ledger record

Rev 21 — replaces the old run entirely. Through rev 20, run was a display state computed from last_run_at inside a 120-second window, refreshed by PostToolUse for a hard-coded list of mutating tools. That is deleted. It violated invariant 2 by inferring a state from a clock, and it was inverted for the case it existed to show: PostToolUse fires on tool completion, so a ten-minute build emitted no signal while it ran and lit the bolt only after it finished.

A bounded stretch of work against exactly one deliverable. Declared open when the work starts, declared closed when it ends. Both ends are written by Claude — nothing is sampled, timed out, or inferred.

Intent, not scope
A run declares what the work is, not how big it is or what it will produce. Scope routinely changes mid-run — a one-line fix becomes a test rewrite and two commits — and that does not make the declaration wrong. The service must never ask for a prediction of duration or of how many events will follow.
Why two calls, when an event is one
Because the knowledge is asymmetric. Claude does know, in advance, that it is starting a bounded piece of work on a known thing — so a run can be declared at its front edge. Claude does not know in advance that a decision is about to be made or a message about to be sent; those are recognised only as they happen. Runs therefore get an open and a close; events stay a single call. No forward phase is forced onto objects that do not have one.
Endings

A run ends in exactly one of two declared ways — closed (the deliverable advanced; the close carries its new state) or abandoned (the work went nowhere; the deliverable is untouched). There is no third ending and, deliberately, no timeout — a timeout would reintroduce exactly the inference rev 21 deletes. A session that crashes mid-run leaks an open run, which is the same known gap as a crashed session holding status="active", repaired by the same future mechanism.

How it hangs together

Work happens in sessions. Everything the ledger knows arrives as one of two kinds of knowledge — what can be witnessed, and what must be judged — and everything anyone sees comes back out as a projection. (Witnessed knowledge arrives through the hooks; judged knowledge through the skill. See How it runs for both in operation.) This panel is the principle; the two panels after it are the details.

Hooks write what can be witnessed. Session lifecycle is mechanical — a launch, a prompt, a tool call, an exit are observable moments. Hooks are involuntary: they fire from Claude Code's own lifecycle, in their own OS process, independent of the skill and of Claude entirely, so the telemetry plane is complete by construction. No judgment is involved, and none is allowed.

The skill writes what must be judged. No sensor can see that a diff was a deliverable or that a conversation settled a decision. The only agent positioned to know is the one doing the work — so Claude logs its own work as a standing duty, triggered by the work itself, never by the user narrating it. That is the record plane.

Neither writer is trusted. The service validates every write, stamps every timestamp, commits composites atomically, and is the only writer of every status. A missed signal costs a stale status until the next signal overwrites it — or, for a crashed session, until a repair mechanism is added (deferred). The one loss the design cannot derive back is an unlogged event — which is exactly why logging is a duty, not a request.

Event emission rules

What it takes for an event to exist, split exactly where invariant 8 puts the seam: the service enforces shape — it can reject, but it never decides what is worth recording; the skill enforces judgment — it decides what happened, but it never decides what is valid. Both halves are binding.

Skill-enforced — judgment; no sensor can see any of this
  1. What qualifies. A deliverable shipped · a decision made · an external communication sent · a stream changing state · an open loop opened or closed. Not: routine lookups, intermediate steps, or anything reconstructible from git or the tool it lives in.
  2. One event per outcome, at completion. Not per step, not per tool call. A long session that ships one thing emits one event.
  3. Self-triggered. Claude logs because the work happened — never because the user narrated it, and never asking permission first. The record's completeness cannot depend on the user remembering.
  4. Stream discipline. Every event names its stream; a genuinely new thread of work carries create_stream in the same call; ledger-system work goes to meta. If the outcome changed the thread's state or next action, the stream_update rides in the same transaction — never a second call.
  5. Corrections are new events. An event is never edited or deleted; a later event supersedes it. The journal is a record of what was believed when, not a tidy summary.
  6. When to open a run. At the front edge of work that is bounded, aimed at a known deliverable, and long enough to be worth watching — minutes, not seconds. The open costs a call, so too low a bar makes it overhead on everything. Declare the intent, never a prediction of scope or duration; scope routinely changes mid-run and that does not make the declaration wrong.
  7. Every run gets closed. Closed if the deliverable advanced, abandoned if it did not — both declared, neither inferred. Leaving a run open is the one way this plane can lie on the board.
Why the seam is here. The service cannot know that a diff was a deliverable, and the skill cannot be trusted to be consistent about shape. Each layer enforces what only it can see — which is the whole of invariant 8.
