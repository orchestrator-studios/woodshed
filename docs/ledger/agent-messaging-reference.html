Claude Code · inter-agent messaging

rev 3 · fact-checked against official docs 2026-09-12 · items marked verify aren't confirmed in the official docs
An idle session is the listener.

Every Claude Code session runs one turn loop. Anything that lands in its inbox is read between tool calls while a turn is running, or starts a brand-new turn when the session is idle. Subagent results, teammate messages, cross-session messages, channel events and raw socket posts all enter through the same door. You never put a session "into a listening state" — you just stop it, and leave the inbox bound.

Three doors into the inbox

Same loop, different producers. Pick by who is sending.

1 · Raw inbox socket

Per-session Unix domain socket (named pipe on Windows). Any process running as your OS user can connect and post a line. Path is in $CLAUDE_CODE_MESSAGING_SOCKET and /status. Best fit for a queue-bridge daemon.

2 · SendMessage / ListAgents

Claude-to-Claude. One session's model addresses another by name; same tool reaches subagents and teammates. notify_when_idle gives a one-shot "tell me when it's done" without spending tokens in the watched session.

3 · Channels (MCP)

An MCP server that declares claude/channel and emits notifications/claude/channel. Event lands in context as a <channel> tag; two-way via a reply tool. The sanctioned path for CI, webhooks, chat. Research preview.

What "waiting for an agent" really is

A background subagent doesn't block its parent. When it finishes, its result is enqueued on the parent's inbox and SubagentStop fires. The parent reads it at the next between-tools checkpoint, or wakes if idle. Teammates do the same with an idle notification that carries their final answer.

Outbound is hooks

The inbox is how events get in. To get "I'm done" out to something else, use lifecycle hooks: Stop, SubagentStop, TeammateIdle, TaskCompleted. Hooks inherit the session's socket path and token, so a hook can publish to your queue and even post back into its own session.

Message outcome rules (no explicit setting)

  • Receiver prompts for permissions → deliver, unless sender claims bypass → hold.
  • Receiver bypasses permissions → hold, unless sender also bypasses → deliver.

SendMessage

Deliver plain text to an agent by name: a subagent in this session, a teammate, another local session, or a cloud / Remote Control session.

Inputs
to (a name from ListAgents — a bare name that uniquely matches delivers; append its [ref] only when a listing or an error shows one), message (plain text), summary (5–10 word one-line UI preview), notify_when_idle (bool)
Refused when
addressed to self · over ~1M chars · burst limit hit · reply target fails safety check
Receiver sees
the text wrapped as <cross-session-message from="…">; told it came from another Claude, not the human. Replying = copying the from attribute as the new to.
Can't do

ListAgents

Enumerates reachable agents: subagents, teammates, local sessions with a bound socket, and (while on Remote Control) cloud and other-machine sessions. Same info as /list-agents.

Agent

Spawns a subagent. With agent teams enabled, a call that passes a name launches a teammate instead (unless it's a fork or passes isolation). run_in_background: true makes the result arrive as an inbox event.

CLAUDE_CODE_MESSAGING_SOCKET

This session's inbox path (uds:-prefixed in /status). Exported to hooks and Bash before SessionStart runs. Each session exports its own; never inherited from a parent.

CLAUDE_CODE_MESSAGING_TOKEN

Per-session secret. Send as the first line {"type":"auth","token":"…"}. Optional on macOS/Linux/WSL 2, required on native Windows. On macOS after the poster exits, and in PID-1 containers, the token is the only way an own-child post is verified.

CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS experimental

1 enables teams (interactive sessions only; -p never spawns teammates). 0 in user settings makes named subagents plain subagents again. Re-read on every spawn, no restart needed.

crossSessionInbound

accept
deliver every message
hold
show a notice, don't deliver; released if accept later applies
refuse
drop silently; sender told not to retry
unset
per-message decision by permission class (see Object model tab)
Scope
project/local refuse beats everything; --settings value is the right place for a worker

dialogExpiry

How long a default-held message waits for approval. 5 minutes by default; "never" keeps it until the session ends. In -p sessions this is the drop deadline, since no dialog can be shown.

isolatePeerMachines

true requires your approval before any message leaves the machine, even in bypass mode. Any scope can turn it on; none can turn it off.

permissions.deny: ["SendMessage","ListAgents"]

Removes the tools entirely, including messaging to subagents and teammates. Combine with crossSessionInbound: refuse to fully silence a session or org.

SessionStart

Fires on start and resume. Socket path and token are already in its environment. Ideal place to register {name, socket, cwd} in your own service registry.

Stop

Fires when the main turn is about to end. Exit 2 with a reason keeps Claude working (check stop_hook_active to avoid loops). Exit 0 and publish "done" to your queue — this is the outbound edge of the loop.

SubagentStop

Fires when a subagent completes. Payload includes the agent id, agent type (matcher key), and the subagent's transcript path. Stop hooks declared inside an agent definition are converted to SubagentStop automatically.

TeammateIdle experimental

Fires when a teammate is about to go idle. Exit 2 sends feedback and keeps it working. team_name in the payload is deprecated.

TaskCreated / TaskCompleted experimental

Gate the shared task list: exit 2 blocks creation or completion and feeds the reason back. Useful for publishing task-state changes to an external tracker.

Notification

Fires when Claude Code surfaces a notification (permission prompt, idle prompt). Purely informational, no blocking. Good for "agent needs a human" alerts.

--name / /rename

Gives a session a stable address. Collisions with a live session get renamed to a variant. Use predictable names so bridges and prompts (@api-worker) can target them. The @ typeahead needs v2.1.232+.

/list-agents (alias /peers) · /status

/list-agents first line is this session's own name; rows are reachable agents with working directories. If the command isn't recognized, the session lacks messaging (check claude --version, need ≥ 2.1.224). /status shows the Peer address row.

-p · --settings · bare mode

-p binds a socket and is listed. Pass --settings '{"crossSessionInbound":"accept"}' so it takes messages unattended. Bare mode binds nothing. A -p run ends when its turn ends, so a long-lived listener is usually an interactive session in tmux or a background session.verify

--channels research preview

Enables a channel plugin for the session (--channels plugin:discord@claude-plugins-official). Custom servers need --dangerously-load-development-channels server:<name> verify (flag confirmed; the server: syntax isn't spelled out in the docs). Requires claude.ai or Console auth; not on Bedrock / Vertex / Foundry. Team & Enterprise orgs must enable. The v2.1.80+ floor appears nowhere in the docs.verify

Socket wire format

connect(uds path)                      # or named pipe on Windows
→ {"type":"auth","token":"$CLAUDE_CODE_MESSAGING_TOKEN"}\n   # optional (required on Windows)
→ <one complete line: the message>\n                       # schema not spelled out in docs
close()                                # within 30 s of connect

The docs describe the auth line and the one-line-within-30-seconds rule but don't publish the message line's JSON shape.verify Cheapest way to learn it: a Stop hook that posts back to $CLAUDE_CODE_MESSAGING_SOCKET, then inspect with --debug.

Channel protocol (MCP)

// server capability
capabilities: { "claude/channel": {} }

// push an event
server.notification({
  method: "notifications/claude/channel",
  params: { content: "CI failed on main: 3 tests", meta: { source: "ci", run: "8812" } }
})
// → <channel source="ci" run="8812">CI failed on main: 3 tests</channel>

// two-way: expose a tool Claude calls to reply

The capability string claude/channel and method name notifications/claude/channel weren't found in the main channels doc — confirm against the channels reference before building on them.verify

Decision path

  • Sender is another Claude session on the same box → SendMessage, add notify_when_idle for completion.
  • Sender is a hook, script or daemon you control on the same box → inbox socket.
  • Sender is out on the network (CI, webhook, Slack) → channel, or a channel fronted by a webhook gateway.
  • You want peers debating inside one terminal, no infra → agent teams.
  • You need durable queues, retries, structured payloads, and no dependence on preview flags → your own harness around the Agent SDK, with Claude Code sessions as optional workers.

Gotchas that bite first

  • Bypass-permissions workers hold unverified messages by default. Set crossSessionInbound: accept explicitly.
  • Containers: sessions inside and outside can't see each other's sockets. WSL 2 and native Windows are separate worlds too.
  • Bursts are refused at the sender; identical repeats are dropped; queue caps at 50. Batch into one message.
  • Messages are text. Put a correlation id and a topic in the first line so the receiving model can route.
  • Permission boundaries are per-session: a session must never ask a peer to do what its own permissions blocked (permission laundering). The receiving model is told this; don't design flows that depend on it.
  • Teammates don't restore after /resume and team config is removed at session end — but the shared task list persists. Teammates can't run background subagents.

A queue bridge, one per agent

Keep Claude Code stock. All the queue logic lives in tiny sidecars; the session only ever sees "a line arrived on my inbox".

How this maps to the ledger

This chapter and the ledger's BotBeam architecture are complementary, not competing. The ledger's /ledger API is the system of record for session state (Phase 1's W1 hook transmitter is exactly the "outbound is hooks" pattern below — Stop/SessionStart hooks posting to a service). What this chapter adds is agent-to-agent tasking: waking a session with work. If we build that, the registry topic below is redundant — BotBeam's session store already knows every session; a bridge would look up sockets there instead of Redis.

1 · Register sessions on start

A SessionStart hook writes the address your bridges need. Fires on resume too, so the record self-heals.

// .claude/settings.json (project)
{ "hooks": { "SessionStart": [{ "hooks": [{ "type": "command",
    "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/register.sh" }] }] } }

# register.sh — stdin is the hook JSON; env has the socket
name=$(jq -r '.session_name // empty' | sed 's/^$/unnamed/')   # field name: verify
redis-cli HSET cc:registry "$name" "$CLAUDE_CODE_MESSAGING_SOCKET"

Exact payload field names for the session name aren't confirmed here.verify The socket path in $CLAUDE_CODE_MESSAGING_SOCKET is documented.

2 · Publish "done" from a Stop hook

{ "hooks": { "Stop": [{ "hooks": [{ "type": "command", "async": true,
    "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/publish-done.sh" }] }] } }

# publish-done.sh
payload=$(cat)                                  # hook JSON: session_id, transcript_path, stop_hook_active…
[ "$(echo "$payload" | jq -r .stop_hook_active)" = "true" ] && exit 0
summary=$(tail -c 4000 "$(echo "$payload" | jq -r .transcript_path)" | your-summarizer)
redis-cli XADD agent.done '*' from "$NAME" corr "$CORR" summary "$summary"
exit 0                                          # never exit 2 here, or the turn won't end

Use SubagentStop the same way if the unit of work is a subagent, and TaskCompleted if you're using the shared task list. Keep the summary short: the next agent gets it as plain text.

3 · Bridge inbound: queue → socket

// bridge.ts (one process per agent, runs as your user)
const sock = await registry.lookup(AGENT_NAME);
for await (const ev of queue.subscribe(`agent.${AGENT_NAME}.inbox`)) {
  const line = renderOneLine(ev);           // topic + corr id first, then the body
  const c = net.connect(sock);              // connect only when the line is ready
  if (process.env.CLAUDE_CODE_MESSAGING_TOKEN)
    c.write(JSON.stringify({type:"auth", token:process.env.CLAUDE_CODE_MESSAGING_TOKEN})+"\n");
  c.write(line + "\n");                     // message-line schema: verify
  c.end();
  await queue.ack(ev);
}

If you'd rather stay on the sanctioned path, make the bridge a channel MCP server instead: same loop, but emit notifications/claude/channel and start the session with --dangerously-load-development-channels server:bridge.

4 · Launch workers that accept unattended

# interactive worker in tmux (survives idle, shows dialogs, listed in /list-agents)
tmux new -d -s worker-b "claude --name worker-b"

# headless worker for a bounded job
claude -p --name worker-b \
  --settings '{"crossSessionInbound":"accept","dialogExpiry":"never"}' \
  "Wait for instructions from the queue bridge and act on them."

Naming matters twice: it's the SendMessage address for other agents, and the registry key for your bridges.

Checklist

  • claude --version ≥ 2.1.224 (2.1.234 on native Windows); /list-agents is recognized
  • Every worker launched with --name
  • crossSessionInbound set explicitly on every worker (accept), or deliberately left to default and understood
  • All posters run as the same OS user; no container boundary between poster and session
  • Stop hooks exit 0 and never re-trigger when stop_hook_active is true
  • Bridge batches bursts into one line; carries a correlation id in the first line
  • Sandbox: sandbox.network.allowUnixSockets (list) includes the socket dir — or allowAllUnixSockets — if Bash posts from inside the sandbox
  • A dead-letter path for messages a session held and expired (5 min default)
